01 · Why local

Why run AI on your own machine?

  • OfflineThe model works on a flight, on a train, anywhere — no connection required.
  • PrivacyYour prompts and data stay on your machine. Nothing leaves the room.
  • Saving moneyYou already paid for the hardware. Stop paying again for the tokens.

This started as curiosity — and a few early mistakes, like pointing Ollama at an M1 from inside VS Code and wondering why it crawled. Those mistakes became this talk.

02 · The comparison

Is there still a gap?

A local open-weight model — Qwen3.8-27B-MLX-4bit — measured against a frontier model, gpt-6-luna.

03 · One key concept

Dense vs. sparse (MoE)

  • DenseUses all parameters for every token — the full toolkit, every time.
  • Sparse / MoEActivates only selected experts per token — far less compute per word.

Either way, all of the model's weights still need to fit in memory — MoE reduces the work per token, not the size on the shelf.

Tools like LMFIT help match a model to your hardware.

04 · Hardware

Local AI boils down to two numbers

  • RAMCan it fit? Capacity decides whether the model runs at all.
  • BandwidthHow fast can it generate? GB/s shapes tokens per second.

04 · Hardware — Capacity

RAM is the hard constraint

Memory use is the model weights plus the KV cache — the running record of your conversation. The cache grows with context length, and its size depends on the architecture and cache precision.

Estimated memory figures — provisional, not verified specifications
Model Assumed architecture Weights KV @32K KV @128K KV @256K Machine RAM @128K
Qwen3.8-27B-MLX-4bit Dense; ~48 layers / 8 KV heads ~14.5 GB ~6 GB ~24 GB ~48 GB 64 GB rec.; 48 GB tight
Gemma-4-26B-A4B-it-QAT-MLX-4bit MoE; 26B total / 4B active; hybrid attention ~14 GB ~3 GB ~13 GB ~26 GB 48 GB
Qwen3.5-9B-MLX-4bit Dense; ~36 layers / 8 KV heads ~5 GB ~4.5 GB ~18 GB ~36 GB 32 GB tight

Estimates, not official specifications. 4-bit weights ≈ ~0.5 bytes/parameter + ~7% overhead. KV cache assumes FP16: 2 × layers × KV heads × head dimension × 2 bytes per token; layer/head counts are assumptions. Machine RAM budgets ~8 GB for the OS and apps. A 4-bit KV cache can cut cache memory to roughly a quarter of FP16 (model/runtime dependent) — don't mix with the FP16 figures above. Actual numbers depend on architecture, runtime, context, and quantization.

04 · Hardware — Speed

Bandwidth is the speed

RAM is whether the car fits in the garage.
Bandwidth is how quickly it travels on the highway.

tokens/s ≈ memory bandwidth (GB/s) ÷ GB of weights read per generated token

  • Qwen3.8-27BDense — ~14.5 GB read per token → ~15 tok/s
  • Gemma-4 A4BMoE — ~2.5 GB active read per token → ~80 tok/s
  • Qwen3.5-9BDense — ~5 GB read per token → ~44 tok/s

Indicative estimates at an illustrative 200 GB/s. Real results are often ~60–80% of the estimate and depend on hardware, runtime, context length, and implementation. For MoE, active parameters set the per-token work — all weights still sit in RAM. Input prefill is often faster than token generation, but the two behave differently.

05 · Software

Two layers: server + harness

  • ServerRuns the model — turns the weights into a serving engine.
  • HarnessSupplies the prompt and presents the result — your interface to the model.

05 · Software — Server

Choose a server, keep the defaults

  • MLXOptimized for Apple Silicon — the natural first choice on a Mac.
  • GGUFCross-platform — runs almost anywhere, not always as tuned on Mac.

Start with default configurations. The source outline recommends avoiding Ollama here: its abstraction layers can trade away inference performance compared with running the server closer to the metal — a trade-off, not a universal law.

05 · Software — Harness

The harness tax

  • Heavier IDEs(e.g. VS Code) may add system prompts and context overhead to every request.
  • Lighter clients(e.g. Pi) keep more of the context window for your actual work.

06 · Closing

An honest take

Frontier tools are easier — zero setup, excellent answers. They remain a strong choice.

Local models are sufficient for many everyday tasks — writing, coding, research, brainstorming. In return you get privacy by default, no subscription or rate limits, and availability anywhere. The trade-off: setup effort, hardware limits, and a gap that still shows on the hardest problems.

We're no longer talking about someday

The question isn't whether local AI can compete.

It's whether you're ready to stop paying for what you can run yourself.
